## Current state (shipped & live)

| Feature | What it does |
|---|---|
| **Local audio transcription (MLX Whisper large-v3)** | Transcribes recordings entirely on-device with MLX Whisper (default full large-v3 on Apple Silicon), with anti-hallucination decoding settings, silero-VAD-based removal of segments outside detected speech, repetition-loop collapse, and an on-disk per-recording transcript cache so reruns are free. |
| **Speaker diarization (pyannote, on-device)** | Runs pyannote speaker-diarization-3.1 locally (Apple-GPU MPS with CPU fallback) to produce who-spoke-when turns plus one embedding per speaker, converts audio to clean 16kHz WAV via ffmpeg to avoid MP3 sample-count bugs, aligns Whisper segments to speakers by max overlap, and caches results per recording. |
| **Speaker recognition via local voiceprint library** | Names anonymous diarized speakers by cosine-matching their embeddings against a private SQLite voiceprint store that keeps every enrolled raw sample as a prototype plus a running-average centroid fallback; matching is precision-first at threshold 0.75, and unmatched voices become Guest N instead of a wrong name. Supports enroll, undo (delete prototype + recompute centroid), and rename-with-merge. |
| **Multilingual per-speaker-block transcription (Chinese/English)** | Detects meetings with a substantial Chinese share by sampling diarization blocks, then transcribes those meetings per speaker-block with per-block language detection so each turn keeps its original language instead of being translated; includes script-based language override, forced re-transcription of misdetected blocks, and noise/repetition cleanup. Detection flags and per-block results are cached. |
| **AI meeting summarization (OpenAI or Claude, structured output)** | Sends the speaker-labeled transcript text to the user-chosen provider — OpenAI or Anthropic — under a shared JSON schema and Circleback-style system prompt, producing an English title, overview bullets, topic sections, and owner-attributed action items; the provider is selected at runtime from configuration. |
| **Notion meeting-notes publishing with playable embedded audio** | Renders each meeting into a Circleback-style Notion page (overview, topic sections, to-do action items, metadata, attendees table, full transcript) via the Notion API, and updates the existing page in place on reruns instead of duplicating it. Uploads the recording's MP3 through Notion's file-upload API (single-part, up to Notion's ~20MB limit) so the page embeds a playable audio block; when the upload fails or the file exceeds the limit, the page falls back to a 'view recording in Riffado' link instead of an embedded player. |
| **Local notes dashboard (web app on 127.0.0.1)** | A FastAPI web app bound to 127.0.0.1 serves a notes list and per-meeting detail pages (summary, action items, attendees, transcript) read from a local SQLite notes store, serves the original recording for in-browser playback with a path-traversal guard, and supports a 'local' destination that stores the published notes only on-device. Note: even with the local destination, the AI-summarization step still sends the transcript text to the configured OpenAI/Anthropic API; it is the storage and viewing that stay local. |
| **In-app speaker naming (Speaker Key: enroll, back-fill, undo, rename)** | The dashboard's Speaker Key panel plays an ffmpeg-extracted per-speaker audio snippet, lets the user name a voice in one click — which enrolls the voiceprint, relabels the meeting locally, and asynchronously back-fills past meetings keyed by identity — and offers undo-last-naming and rename-everywhere (with voiceprint merge). Renames of already-published meetings are queued and re-published to Notion by the worker. |
| **Hands-off scheduling via launchd with idempotent catch-up** | A launchd agent (shipped as com.plaudautomation; installed on this machine as net.bhangar.plaudautomation) runs the sync-and-reconcile entry point every 30 minutes and at load/login, with launchd firing deferred intervals after wake; the reconciler processes only recordings not yet marked processed in a SQLite ledger, skips short/trashed/skip-listed recordings, and continues past per-recording failures. The live log shows runs completing today. A second KeepAlive agent for an always-on dashboard web server is shipped as a plist template and installable via the wizard's one-click launchd step, but is not currently installed or running (no web agent in ~/Library/LaunchAgents; nothing listening on 127.0.0.1:8787). |
| **Plaud cloud sync via self-hosted Riffado (headless trigger + hardened deployment + watchdog)** | Integrates with a self-hosted Riffado container that syncs recordings from Plaud cloud: a read-only paginated API client lists/downloads recordings, and a headless BetterAuth session login triggers server-side sync from launchd (working in today's logs). The shipped docker-compose requires an explicitly pinned image version (it refuses to start without RIFFADO_VERSION set — no :latest), binds the app port to 127.0.0.1 only with Postgres not published at all, and configures away the app's non-Plaud egress (GitHub update check disabled; S3/SMTP/analytics/public-webhooks left unset) — an app-config restriction, not a network-enforced egress block. A launchd watchdog running every 5 minutes restarts Docker and the containers when port 3000 stops answering. |
| **Telegram failure and crash alerts (deduplicated)** | Pings a configured Telegram chat when recordings fail or the scheduled run itself crashes, deduplicating per (recording, error) and per crash-error string in a state file so a 30-minute crash loop alerts once, clearing recovered recordings so a later regression re-alerts; only the recording id and a trimmed error string are sent. |
| **Browser-based setup wizard (guided install, live logs, key testing, cost estimates)** | First run serves a two-step wizard that installs the pipeline (ffmpeg, Python 3.12, ML venv, Riffado via docker compose, launchd agents) with per-step detection, live install logs streamed over SSE, and one-click launchd bootstrap; the configure step writes destination/provider choices and chmod-600 secrets, offers Test buttons that probe Riffado/Notion/OpenAI/Anthropic/HuggingFace credentials, and shows per-model summary-cost ranges per 100 meetings. |
